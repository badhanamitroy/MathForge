# MathForge Phase 3D — Storage Adapter Specification

**Status:** Proposed contract; audit only  
**Applies to:** Native SQLite desktop adapter and SQLite WASM browser adapter  
**Schema version described:** 2

## 1. Contract principles

- One async API and one versioned document format across desktop and browser.
- No cloud service/account. Adapter selection and persistent-storage failure are visible to the user.
- Tools exchange validated plain JSON and asset references; they never issue SQL.
- Keep project metadata relational and tool-specific document state as JSON snapshots.
- IDs are generated by the app. A project may contain multiple documents and tool types.
- Distinguish the app catalog database from a portable one-project `.mathforge` database.
- Do not claim save success before the platform transaction is durable/committed.
- Trash is recoverable soft deletion; it retains project data and versions until explicit permanent purge.

## 2. Suggested JavaScript interface

All methods return Promises. Errors reject; do not return `null`, empty lists, or success-shaped defaults after a storage failure.

```js
storage.initialize({ mode: "catalog" | "portable", fileHandle? })
storage.createProject({ title, documents? })                  // -> ProjectSnapshot
storage.openProject({ projectId })                            // -> ProjectSnapshot
storage.saveProject({ projectId, documents, expectedRevision })
storage.saveAs({ projectId, title?, expectedRevision })        // -> ProjectSnapshot
storage.listProjects({ query?, includeTrash?, limit?, offset? })
storage.renameProject({ projectId, title })
storage.duplicateProject({ projectId, title? })                // -> Project
storage.deleteProject({ projectId })                           // -> trashed Project
storage.restoreProject({ projectId })                          // -> restored Project
storage.purgeProject({ projectId, confirmToken })              // irreversible
storage.exportProject({ projectId })                           // -> Blob/bytes or host file result
storage.importProject({ source, conflict: "copy" | "replace" }) // -> Project
storage.listVersions({ projectId, limit? })                    // -> VersionSummary[]
storage.restoreVersion({ projectId, versionNo, expectedRevision }) // -> ProjectSnapshot
storage.close()
```

`initialize()` reports an explicit capability result (selected backend, persistence status, read-only status, schema version, and any degraded capability). A caller must not continue as though storage were durable if initialization failed. Browser implementation can additionally expose `requestPersistentStorage()` and `getStorageEstimate()` as capability methods; they do not alter core CRUD semantics.

### Complete operation contract

Every method returns a Promise. The result column defines its resolved value; operations reject with the listed stable errors and shared errors in Section 4. Every mutating operation resolves only after its transaction commits, and either all described effects commit or none do. An error preserves the platform exception as its cause.

| Method and arguments | Return value | Errors and transaction behavior |
|---|---|---|
| `initialize({ mode, fileHandle? })` | `StorageCapabilities` (backend, persistence/read-only flags, schema version, degraded capabilities) | `STORAGE_UNAVAILABLE`, `PERMISSION_DENIED`, `SCHEMA_TOO_NEW`, `MIGRATION_FAILED`. Opens/validates or migrates; failed migration leaves the database at the prior schema. |
| `createProject({ title, documents? })` | `ProjectSnapshot` | `INVALID_DOCUMENT`, `TRANSACTION_FAILED`. Project, documents, initial version, assets, and links are one transaction. |
| `openProject({ projectId })` | `ProjectSnapshot` including revisions and referenced assets | `PROJECT_NOT_FOUND`, `PROJECT_TRASHED`, `INVALID_DOCUMENT`, `CORRUPT_DATABASE`. Consistent read; update recent-project row only after validation, in a transaction. |
| `saveProject({ projectId, documents, expectedRevision })` | `{ projectId, revision, documents: [{ documentId, revision }], savedAt }` | `PROJECT_NOT_FOUND`, `PROJECT_TRASHED`, `REVISION_CONFLICT`, `INVALID_DOCUMENT`, `QUOTA_EXCEEDED`, `TRANSACTION_FAILED`. CAS, document/asset writes, revision increments, and any due snapshot are atomic. |
| `saveAs({ projectId, title?, expectedRevision })` | New `ProjectSnapshot` with remapped project/document/asset/version IDs | `PROJECT_NOT_FOUND`, `PROJECT_TRASHED`, `REVISION_CONFLICT`, `TRANSACTION_FAILED`. Read source at expected revision and create target with its initial snapshot in one transaction. |
| `listProjects({ query?, includeTrash?, limit?, offset? })` | Bounded `ProjectSummary[]`, excluding Trash unless requested | `STORAGE_UNAVAILABLE`. Read-only; summaries include `trashedAt` and recent-open time where available. |
| `renameProject({ projectId, title })` | Updated `Project` | `PROJECT_NOT_FOUND`, `PROJECT_TRASHED`, `TRANSACTION_FAILED`. Metadata-only transaction; content revision is unchanged. |
| `duplicateProject({ projectId, title? })` | New `ProjectSnapshot` | `PROJECT_NOT_FOUND`, `PROJECT_TRASHED`, `TRANSACTION_FAILED`. Remap IDs and references atomically; target has an `initial` snapshot. |
| `deleteProject({ projectId })` | Project summary with non-null `trashedAt` | `PROJECT_NOT_FOUND`, `TRANSACTION_FAILED`. Set Trash marker and remove recent row in one transaction; retain content, versions, and assets. |
| `restoreProject({ projectId })` | Active `Project` with `trashedAt: null` | `PROJECT_NOT_FOUND`, `TRANSACTION_FAILED`. Clear Trash marker transactionally; do not add a recent row until a successful open. |
| `purgeProject({ projectId, confirmToken })` | `{ projectId, purged: true }` | `PROJECT_NOT_FOUND`, `CONFIRMATION_REQUIRED`, `TRANSACTION_FAILED`. Irreversible transaction; remove reference links, then delete project and cascade owned rows. |
| `exportProject({ projectId })` | Completed `.mathforge` `Blob`/bytes or host file result | `PROJECT_NOT_FOUND`, `EXPORT_FAILED`, `CORRUPT_DATABASE`. Consistent read/backup; source is unchanged. |
| `importProject({ source, conflict })` | Imported `ProjectSnapshot` | `INVALID_PROJECT_FILE`, `SCHEMA_TOO_NEW`, `CORRUPT_DATABASE`, `IMPORT_FAILED`, `TRANSACTION_FAILED`. Stage and validate before a single catalog transaction; `copy` allocates new IDs, `replace` requires explicit target confirmation. |
| `listVersions({ projectId, limit? })` | Bounded `VersionSummary[]`, newest first | `PROJECT_NOT_FOUND`, `STORAGE_UNAVAILABLE`. Read-only; metadata only. |
| `restoreVersion({ projectId, versionNo, expectedRevision })` | Restored `ProjectSnapshot` with monotonic revisions | `PROJECT_NOT_FOUND`, `PROJECT_TRASHED`, `REVISION_CONFLICT`, `INVALID_PROJECT_FILE`, `TRANSACTION_FAILED`. CAS, before-restore snapshot, document/link replacement, and revision increments are atomic. |
| `close()` | `{ closed: true }` | `CLOSE_FAILED`, `TRANSACTION_FAILED`. Stop new writes, await queued commits, and release handles; pending-write failures are reported. |

### Data shapes and version fields

`Project` contains `{ projectId, title, createdAt, updatedAt, formatVersion, revision, trashedAt }`.

`ProjectSnapshot` contains the project metadata plus:

```json
{
  "revision": 12,
  "documents": [
    {
      "documentId": "opaque-id",
      "toolType": "coordinates-graph",
      "title": "Coordinates",
      "documentSchemaVersion": 1,
      "revision": 5,
      "state": {},
      "assetIds": []
    }
  ]
}
```

- `projects.revision` is the project-level **content revision**. It increments once per successful save transaction that persists changed document content. It is the compare-and-swap token (`expectedRevision`) across the complete project.
- `project_documents.revision` is that document's **content revision**. It increments when that document's persisted content changes; a new document starts at 1.
- `project_documents.document_schema_version` describes the JSON structure/version understood by tool serializers and migrations. It is not a content revision and does not change just because the user edits content.
- `projects.format_version` describes the portable project/database format compatibility. It is not either document field.

`documentSchemaVersion` changes only through an explicit, validated document migration. Migrations preserve user state and run before exposing the document to a tool. `revision` values are monotonic within a project/document lifetime; restore creates a new content revision rather than rewinding counters. A new project is created at project revision 1 when it has initial documents (0 when empty), and its initial snapshot records that revision.

The `state` object retains user-authored raw input. Every tool document must have a validator and deterministic capture/restore pair. Canvas pixels, DOM nodes, event handles, and transient gestures are not document state.

## 3. Operation semantics

| Operation | Required behavior |
|---|---|
| `createProject` | Validate nonblank title and all documents before opening a write transaction. Insert project, initial documents, set initial project revision, create version 1 with reason `initial`, and insert all asset links atomically. Any failure rolls all of it back. |
| `openProject` | Reject a trashed project unless an explicit trash/recovery flow requests it. Read project/documents/assets consistently. Validate known document versions; preserve unknown fields only when explicitly forward-compatible. Update recents after successful open. |
| `saveProject` | Within one write transaction compare `expectedRevision` to the current project revision. A stale token returns `REVISION_CONFLICT`. Persist every validated changed document and assets; increment each changed document revision; only after those writes succeed, CAS-increment project revision exactly once. Optional checkpoint and its asset links are in the same transaction. Commit before reporting success. On any failure roll back documents, assets, and revisions. A no-op save may return the unchanged revision after verifying the token. |
| `saveAs` | Create a distinct project and copy document data/asset contents; never mutate the original or share mutable asset IDs between projects. Create the target initial snapshot atomically. |
| `listProjects` | Return stable summaries with bounded pagination; exclude trashed projects by default. `includeTrash` opts in to trash. Do not load document snapshots or asset BLOBs. |
| `renameProject` | Validate title; one metadata transaction. Does not increment content revision because it does not change document content. |
| `duplicateProject` | One transaction for new project/document/asset/version IDs and rewritten references. Do not reuse source IDs in the target database namespace or preserve foreign-key references to the original. Initial target version reason is `initial`. |
| `deleteProject` | Soft-delete only: set `trashed_at` and `updated_at`, and remove its `recent_projects` row in one transaction; retain documents, assets, and versions. Do not create a `before-delete` version and do not claim permanent deletion. |
| `restoreProject` | Clear `trashed_at` and update metadata in a transaction. Content revisions and retained snapshots remain unchanged. Do not add a recent row until a successful `openProject`. |
| `purgeProject` | Irreversible operation requiring explicit confirmation. In one transaction delete project/version/document asset-link rows first, then delete the project; FK cascades remove documents, versions, project assets, and recents. Design presets are workspace-level and are not project children. |
| `exportProject` | Produce a consistent one-project SQLite file using SQLite's backup/snapshot mechanism. Include project state, retained versions, every current/version-referenced asset and its links, and `trashed_at` if exporting a trashed project. Never copy a live WAL database naively. |
| `importProject` | Stage input in a temporary location/database; check file-size limits, `integrity_check`, schema compatibility, project count, JSON, asset references, and hashes. Commit into catalog only after all checks pass. Preserve trash status only when the user explicitly imports it as trash; default import is active. |
| `listVersions` | Return metadata only, newest first and bounded. |
| `restoreVersion` | In a single transaction create a `before-restore` snapshot of current content, replace current documents and asset links from the selected snapshot, increment affected document and project content revisions (never rewind), record the new revision, then commit. Roll back completely on any error. |
| `close` | Stop accepting writes, await/flush queued operations, close DB and worker/native handles, release locks, and report failures. It is not the primary autosave trigger. |

## 4. Compare-and-swap and transaction policy

Use one serialized writer queue per project. SQLite `BEGIN IMMEDIATE` acquires the write transaction before reading the expected revision. The check and all writes must remain in that transaction. The final project update must still contain `WHERE project_id = :id AND revision = :expected_revision AND trashed_at IS NULL`; require exactly one affected row. If not, roll back and return `REVISION_CONFLICT`. This protects against stale callers and accidental transaction-policy changes.

For example:

```sql
BEGIN IMMEDIATE;
-- Read/check revision inside this transaction; mismatch => ROLLBACK.
UPDATE project_documents
   SET document_json = :json,
       document_schema_version = :schema_version,
       revision = revision + 1,
       updated_at = :now
 WHERE project_id = :project_id
   AND document_id = :document_id;
-- Require one row for an existing document, or insert a new document at rev 1.
-- Any document/asset failure => ROLLBACK.
UPDATE projects
   SET revision = revision + 1, updated_at = :now
 WHERE project_id = :project_id
   AND revision = :expected_revision
   AND trashed_at IS NULL;
-- Require one row. Otherwise ROLLBACK all preceding changes and return
-- REVISION_CONFLICT.
-- Optional version snapshot and project_version_assets links go here.
COMMIT;
```

A failed document write or failed compare-and-swap rolls back all project/document revision updates. Project revision increments once only after the document writes have succeeded. Each modified document revision increments once. Metadata-only rename/trash/restore operations do not alter content revisions. `updated_at` values use one UTC ISO-8601 timestamp captured per transaction.

For SQLite desktop, enable foreign keys on every connection and choose WAL/locking policy for the selected runtime. For browser SQLite, follow the chosen VFS's locking and concurrency rules; do not assume two tabs can write safely because both can open the same OPFS/IndexedDB database. Use an application-level lock/lease or a single shared worker and test lock recovery.

All adapter errors should include a stable code and operation context, while avoiding sensitive project contents in logs:

- `STORAGE_UNAVAILABLE`, `PERMISSION_DENIED`, `QUOTA_EXCEEDED`, `READ_ONLY`, `CONFIRMATION_REQUIRED`
- `PROJECT_NOT_FOUND`, `PROJECT_TRASHED`, `REVISION_CONFLICT`
- `INVALID_DOCUMENT`, `INVALID_PROJECT_FILE`, `CORRUPT_DATABASE`
- `SCHEMA_TOO_OLD`, `SCHEMA_TOO_NEW`, `MIGRATION_FAILED`
- `TRANSACTION_FAILED`, `EXPORT_FAILED`, `IMPORT_FAILED`, `CLOSE_FAILED`

Preserve the original platform exception as a cause for diagnostics. UI may offer retry/export, but it must keep dirty data marked unsaved and must not swallow the failure.

## 5. Migration runner

Use `PRAGMA user_version` as the authoritative ordered database schema version and `schema_migrations` as the audit ledger. Each migration has an immutable integer version, stable key, and ordered SQL/application migration function.

1. Open a read/write connection and enable foreign keys.
2. Read `PRAGMA user_version`. If it exceeds the maximum supported version, close and return `SCHEMA_TOO_NEW`; never downgrade or change the file.
3. Before any production migration, create a SQLite-consistent backup using SQLite's backup API (or quiesce/close and copy all required DB/WAL state). Verify the backup with `PRAGMA integrity_check` and record its location/result.
4. For each registered migration where `version > currentVersion`, apply only the next migration in order, each in its own `BEGIN IMMEDIATE` transaction.
5. In that transaction, execute migration steps and run data validation. Execute `PRAGMA foreign_key_check` and inspect its returned rows; any row is a migration failure and must trigger rollback. Only after checks pass, insert the matching `(version, migration_key, applied_at)` row, set `PRAGMA user_version = version`, then commit.
6. On any failure, roll back that migration, leave `user_version` and its ledger entry unchanged, close the failed connection, and retain the verified backup. Report `MIGRATION_FAILED`; do not open the database as writable.
7. After all migrations, verify `user_version` equals the latest applied migration and the ledger is consistent. Never apply future migrations early or infer schema version from table existence alone.

### Concrete v1 → v2 migration

The v1 proposal's `document_version` was initialized to 1 and had no content-revision behavior. Migration treats that stored value as `document_schema_version` and initializes content revisions to 1 for existing documents/projects with content. New v2 databases use `document_schema_version`, document `revision`, project `revision`, and `trashed_at` separately.

The migration adds project revision/trash columns, rebuilds `project_documents` to remove ambiguous `document_version`, and rebuilds `project_versions` to add `project_revision` and `initial` while removing `before-delete`. It preserves both asset-link tables. Existing `document_version` was initialized to 1 without content revision semantics, so it migrates to `document_schema_version`; existing document/project content revisions initialize to 1 when content exists. Existing `before-delete` rows are retained and normalized to reason `manual` because v1 had no soft-delete contract. Use temporary asset-link copies while rebuilding both parent tables, within the migration transaction:

```sql
BEGIN IMMEDIATE;
ALTER TABLE projects ADD COLUMN revision INTEGER NOT NULL DEFAULT 0
    CHECK (revision >= 0);
ALTER TABLE projects ADD COLUMN trashed_at TEXT;
UPDATE projects
   SET revision = CASE WHEN EXISTS (
       SELECT 1 FROM project_documents d
        WHERE d.project_id = projects.project_id
   ) THEN 1 ELSE 0 END;

CREATE TEMP TABLE saved_document_assets AS
    SELECT project_id, document_id, asset_id, role FROM document_assets;
DROP TABLE document_assets;
CREATE TABLE project_documents_v2 (
    document_id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    tool_type TEXT NOT NULL CHECK (
        tool_type IN ('coordinates-graph', 'equation-plotter',
                      'ogive-curve', 'histogram-polygon')
    ),
    title TEXT NOT NULL,
    document_json TEXT NOT NULL,
    document_schema_version INTEGER NOT NULL DEFAULT 1
        CHECK (document_schema_version > 0),
    revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (project_id, document_id),
    FOREIGN KEY (project_id) REFERENCES projects(project_id) ON DELETE CASCADE
);
INSERT INTO project_documents_v2
    (document_id, project_id, tool_type, title, document_json,
     document_schema_version, revision, created_at, updated_at)
SELECT document_id, project_id, tool_type, title, document_json,
       document_version, 1, created_at, updated_at
  FROM project_documents;
DROP TABLE project_documents;
ALTER TABLE project_documents_v2 RENAME TO project_documents;
CREATE TABLE document_assets (
    project_id TEXT NOT NULL,
    document_id TEXT NOT NULL,
    asset_id TEXT NOT NULL,
    role TEXT NOT NULL DEFAULT 'embedded',
    PRIMARY KEY (document_id, asset_id),
    FOREIGN KEY (project_id, document_id)
        REFERENCES project_documents(project_id, document_id) ON DELETE CASCADE,
    FOREIGN KEY (project_id, asset_id)
        REFERENCES project_assets(project_id, asset_id) ON DELETE RESTRICT
);
INSERT INTO document_assets SELECT * FROM saved_document_assets;
DROP TABLE saved_document_assets;

CREATE TEMP TABLE saved_version_assets AS
    SELECT project_id, version_no, asset_id FROM project_version_assets;
DROP TABLE project_version_assets;
CREATE TABLE project_versions_v2 (
    project_id TEXT NOT NULL,
    version_no INTEGER NOT NULL CHECK (version_no > 0),
    project_revision INTEGER NOT NULL CHECK (project_revision >= 0),
    created_at TEXT NOT NULL,
    reason TEXT NOT NULL CHECK (
        reason IN ('initial', 'manual', 'autosave-checkpoint',
                   'before-restore', 'recovery')
    ),
    snapshot_json TEXT NOT NULL,
    snapshot_sha256 TEXT NOT NULL,
    PRIMARY KEY (project_id, version_no),
    FOREIGN KEY (project_id) REFERENCES projects(project_id) ON DELETE CASCADE
);
INSERT INTO project_versions_v2
    (project_id, version_no, project_revision, created_at, reason,
     snapshot_json, snapshot_sha256)
SELECT v.project_id, v.version_no, p.revision, v.created_at,
       CASE WHEN v.reason = 'before-delete' THEN 'manual' ELSE v.reason END,
       v.snapshot_json, v.snapshot_sha256
  FROM project_versions v JOIN projects p USING (project_id);
DROP TABLE project_versions;
ALTER TABLE project_versions_v2 RENAME TO project_versions;
-- Recreate idx_project_versions_created after replacing the table.
CREATE INDEX idx_project_versions_created
    ON project_versions(project_id, created_at DESC);
CREATE TABLE project_version_assets (
    project_id TEXT NOT NULL,
    version_no INTEGER NOT NULL,
    asset_id TEXT NOT NULL,
    PRIMARY KEY (project_id, version_no, asset_id),
    FOREIGN KEY (project_id, version_no)
        REFERENCES project_versions(project_id, version_no) ON DELETE CASCADE,
    FOREIGN KEY (project_id, asset_id)
        REFERENCES project_assets(project_id, asset_id) ON DELETE RESTRICT
);
INSERT INTO project_version_assets SELECT * FROM saved_version_assets;
DROP TABLE saved_version_assets;
CREATE INDEX IF NOT EXISTS idx_projects_updated ON projects(updated_at DESC);
CREATE INDEX idx_projects_trash ON projects(trashed_at, updated_at DESC);
CREATE INDEX idx_project_documents_project_updated
    ON project_documents(project_id, updated_at DESC);
CREATE INDEX idx_project_documents_tool
    ON project_documents(project_id, tool_type);
CREATE INDEX idx_document_assets_asset ON document_assets(project_id, asset_id);
CREATE INDEX idx_project_version_assets_asset
    ON project_version_assets(project_id, asset_id);
PRAGMA foreign_key_check;
-- The runner must inspect the result above and ROLLBACK if any row is returned.
INSERT INTO schema_migrations(version, migration_key, applied_at)
VALUES (2, 'phase3d-v2-revision-trash', :now);
PRAGMA user_version = 2;
COMMIT;
```

## 6. Asset, snapshot, and deletion integrity

- `project_version_assets` records every asset required by that version's snapshot. Create snapshot JSON and its asset links in one transaction. A retained version's asset FK uses `ON DELETE RESTRICT`; asset GC must exclude all IDs referenced by current documents or retained versions.
- `document_assets` similarly restricts removal of a current asset. GC deletes only unreferenced assets after old versions are pruned. Do not use a cascading asset delete as garbage collection.
- `deleteProject` sets `trashed_at` and removes the `recent_projects` row in the same transaction; no project content or assets are removed. `restoreProject` clears the marker and preserves snapshots, but does not recreate a recent row until the project is opened. There is no automatic Trash expiration in this proposal.
- For explicit `purgeProject`, remove `project_version_assets` and `document_assets` links first, then delete the project in one transaction. Project FK cascades delete documents, versions, project assets, and recent rows. Assets are project-scoped; no asset row is shared across projects. The ordered cleanup satisfies asset RESTRICT constraints and prevents orphan rows. If any step fails, the transaction restores the complete project.
- Duplicate/import operations allocate new project, document, asset, and version IDs as required and rewrite every document/version asset link. Validate that all snapshot asset IDs have matching `project_version_assets` rows and blobs before commit.
- Portable export includes only assets referenced by current documents or retained versions, and includes both link tables. Import stages the complete project, blobs, and links before changing the catalog.

## 7. Autosave, snapshots, and recovery

- Dirty tracking begins at the tool state mutation boundary, not just at a toolbar Save click.
- Debounce for 600 ms and enforce a 5-second maximum delay while edits continue.
- Coalesce obsolete queued snapshots; serialize the latest revision and compare it with the current revision after commit.
- Expose `Unsaved changes`, `Saving…`, `Saved <time>`, or `Save failed`. A failed write does not clear dirty state.
- Snapshot on initial project creation, manual save, before restore, and every five minutes while dirty. Trash does not need a `before-delete` version because it preserves all rows. Retain the newest 25 automatic/manual versions and seven daily checkpoints as an initial policy.
- Mark the session as open/unclean in durable workspace metadata. Clear only after queued writes finish and DB close succeeds. On startup, handle an unclean marker with integrity check and a recovery prompt; never replace the latest valid data silently.
- A version restore first creates a `before-restore` checkpoint. Restore and checkpoint creation share a transaction and advance content revision monotonically.
- `beforeunload` is only an unsaved-changes warning fallback. It must not be treated as a database flush guarantee.

## 8. `.mathforge` import/export contract

A `.mathforge` file is a single-project SQLite database using the versioned schema in [PHASE_3D_SQL_SCHEMA_PROPOSAL.sql](./PHASE_3D_SQL_SCHEMA_PROPOSAL.sql). It contains a project record, documents, retained versions, referenced assets and relationship rows, project revision, document schema/content revisions, and trash status. It must not need a sidecar directory or cloud URL. Workspace settings and recents are local catalog data and are not exported.

Validate extension as a UX hint only; inspect the SQLite file/schema. Enforce file-size limits before allocating large buffers; verify SQLite integrity, schema/format major, supported tool IDs and document schemas, JSON validity/shape, `byte_length`, SHA-256, and all document/version asset references. Import through a temporary/staging DB. Replace/copy choices must be explicit, and no target project changes before full validation. Export via SQLite backup/snapshot API to a temporary target, close/check it, then expose the completed file. On unsupported newer schema, preserve the original file and explain that this app version cannot open it.

## 9. Lifecycle and API consistency

`initialize()` is idempotent for a live adapter; a closed instance requires explicit reinitialization. `close()` is idempotent but reports failed pending writes. After close, all operations reject with `STORAGE_UNAVAILABLE` until initialized again. Provide a readiness promise before binding project actions, and do not let tool selection race project load/restore. Closing/switching tools captures current state and schedules a save; UI must not imply that tool-switching itself is durable until commit completes.
